Modularity Review

Scope: PacMan + Void Arena — matchmaking, settlement, winner announcement, overlays Date: 2026-06-24 Model: Balanced Coupling by Vlad Khononov

Executive Summary

The frontend game plugin contract is well-designed: games receive matchCtx and emit onWinner(address) — a clean, stable boundary that makes adding a new client-side game additive. The problem is on the server side.

server/src/ws/handlers/match.ts has grown into a 520-line file that simultaneously owns match lifecycle orchestration, game engine hosting, peer-relay forwarding, consensus logic, and on-chain settlement. Two of those responsibilities — engine hosting and peer-relay — change every time a game is added or modified, making the stable lifecycle code a casualty of game-level changes. The planned plugin architecture described in docs/game-integration.md (BaseMatch, server/src/games/<slug>/) was never built; instead, PacManServerGame was embedded inline. With all games moving to server-authoritative execution, this gap will compound with each new title.

The second problem is subtler: PacMan and Arena3D use two different server-side execution models (server-authoritative vs peer-relay) with no explicit marker in the shared protocol or registry. The client has no way to know which settlement path a given game will take without reading match.ts. This hidden coupling makes debugging settlement failures difficult — the event sequence differs silently by gameSlug.

Issue 1 — Server Game Engine Embedded in Lifecycle Orchestrator
Integration: PacManServerGame → match.ts
Critical

Knowledge Leakage

PacManServerGame (84 lines — tick loop, input buffering, best-of-3 round logic, server broadcast) is defined directly inside match.ts. The Match interface carries a pacmanGame?: PacManServerGame field. The file imports the game engine at the top level:

import { initGame, update, nextRound, type Dir, type GameState } from '../../games/pacman/engine'

This means match.ts owns knowledge of two separate domains: how a match lifecycle runs (create → join → ready → countdown → begin → settle) and how PacMan ticks (fixed 20ms interval, ghost state, round wins, p1Wins >= 3). These have completely different rates of change.

docs/game-integration.md planned a clean separation — server/src/games/<slug>/<Slug>Match.ts, extending BaseMatch — but it was never built. PacManServerGame is the intended PacManMatch, stranded in the wrong file.

Cascading Changes

  • Add Arena3D server-authoritative → must edit match.ts to embed Arena3DServerGame, extend the Match interface again (arena3dGame?:), add another if (gameSlug === 'arena3d') branch in handlePlayerReady
  • Change PacMan round format (best-of-3 → best-of-5) → game logic lives in match.ts, not with the game
  • Fix a PacMan engine bug → tick interval, broadcast logic, and win condition live in match.ts; the fix requires two files for one game
Recommended Fix

Extract PacManServerGame to server/src/games/pacman/PacManServerGame.ts. Define a GamePlugin interface:

// server/src/games/registry.ts
export interface GamePlugin {
  start(): void
  stop(): void
  handleInput(slot: 1 | 2, input: unknown): void
}
export type PluginFactory = (matchId: string, p1: string, p2: string, onOver: (winner: string) => void) => GamePlugin

const registry = new Map<string, PluginFactory>()
export const registerGame = (slug: string, f: PluginFactory) => registry.set(slug, f)
export const getGame = (slug: string) => registry.get(slug)
// server/src/games/pacman/PacManServerGame.ts
import { registerGame } from '../registry'
// ... PacManServerGame class ...
registerGame('pacman', (matchId, p1, p2, onOver) => new PacManServerGame(matchId, p1, p2, onOver))

match.ts becomes game-agnostic — adding a new game means creating one file and calling registerGame(). match.ts never changes for game content.

Issue 2 — Game-Slug Branching Will Accumulate in match.ts
Integration: per-game if checks in match.ts
Critical

Knowledge Leakage

There are already three game-slug conditionals in match.ts:

// handlePlayerReady — line 271
if (activeBet.gameSlug === 'pacman') { ... }

// handleGameState — line 390
if (match.gameSlug === 'shooter') { ... }   // kill tracking

// handleGameOver — line 458
if (match?.pacmanGame) return               // blocks client reports for server-auth games

Each represents game-specific knowledge that leaked into the lifecycle module. As games are added, this list grows. The change blast radius grows with it: every new game requires reading and editing the 520-line lifecycle file.

Cascading Changes

  • Add a game with server-side kill tracking → add else if (match.gameSlug === 'arena3d') { ... } in handleGameState
  • Add a server-authoritative game → add if (match?.arena3dGame) return in handleGameOver
  • Change a game's slug → find all branch sites in match.ts and update them — no tooling will catch a miss
Recommended Fix

The registry pattern from Issue 1 dissolves all three branches:

// handleGameOver: one check, no game knowledge needed
if (match.serverGame) return   // all server-auth games block client reports uniformly

// handleGameState relay: only fires when no serverGame (peer-relay mode)
if (!match.serverGame) send(other, 'game:state', stateData)

// handleGameInput: plugin decides what to do with input
match.serverGame?.handleInput(actualSlot, dir)

match.ts stops knowing game slugs entirely. Kill tracking, input buffering, and round logic move into each game plugin.

Issue 3 — Two Settlement Paths with No Explicit Marker
Integration: PacMan server-auth path vs Arena3D peer-relay path
Significant

Knowledge Leakage

PacMan and Arena3D reach settlement through completely different event sequences, but nothing in the protocol, the client registry, or the store makes this explicit.

// PacMan (server-authoritative) — client is passive:
server PacManServerGame.onOver(winner)
  → match.terminate(winner) → onComplete(winner)
  → send both: match:settling → settleMatch() → match:settled / match:complete
  ← client never sends game:over

// Arena3D (peer-relay) — client initiates:
client engine: gameOver detected
  → onWinner(addr) → announceWinner() → ws.send('game:over', ...)
  → server consensus (both clients report)
  → match.terminate(winner) → same settlement path

The matchStore handles both paths with the same handlers, but announceWinner sets phase: 'settling' locally before the server responds — only correct for the peer-relay model. For PacMan, phase stays at 'playing' until the server fires match:settling. This asymmetry has already caused bugs (winner stuck on settling, loser missing the result screen — both fixed this session).

When Arena3D moves to server-authoritative, Arena3DGame.tsx's onWinner call must be dropped (like PacMan's _onWinner) — but nothing in the game registry signals this, leaving it as undocumented tribal knowledge.

Cascading Changes

  • Move Arena3D to server-authoritative → must remember to silence onWinner in the component; no code enforces this
  • Add a new server-auth game → developer must know not to call onWinner, discoverable only by reading PacManGame.tsx's _onWinner naming convention
  • Debug a settlement hang → must first determine which execution model the game uses before knowing which event sequence to trace
Recommended Fix

Add serverAuthoritative: boolean to the Game registry in games.ts:

// frontend/src/lib/games.ts
export interface Game {
  slug: string
  title: string
  description: string
  category: 'Arcade' | 'Action' | 'Puzzle' | 'Strategy'
  players: string
  thumb?: string
  serverAuthoritative: boolean   // ← add this
  component: ComponentType<GameProps>
}

matchStore.announceWinner (or GamePage) checks this flag before sending game:over. When Arena3D becomes server-authoritative, flip the flag — no game component code changes required. The execution model is explicit in one place, not inferred from component internals.

Issue 4 — matchStore Event Handler Topology Is Opaque
Integration: 13 ws.on() registrations at store construction
Minor

Knowledge Leakage

All 13 WS event handlers are registered in the create() callback body with no structural grouping. Finding which event causes a specific phase transition requires reading all 13 handlers. The handlers mix three concerns with no visual separation: phase transitions (match:settling, match:begin), timer management (clearWaitingTimer(), clearCountdown()), and re-entry guards (if (get().phase !== 'complete')).

Recommended Fix — Comments Only, Zero Runtime Change
// ── Phase transitions ──────────────────────────────────────────────────────
ws.on('match:waiting', ...)
ws.on('match:countdown', ...)
ws.on('match:begin', ...)
ws.on('match:settling', ...)
ws.on('match:settled', ...)
ws.on('match:complete', ...)

// ── Error terminals ────────────────────────────────────────────────────────
ws.on('match:error', ...)
ws.on('match:disputed', ...)
ws.on('match:cancelled', ...)

// ── Opponent presence ──────────────────────────────────────────────────────
ws.on('match:opponent_joined', ...)

ws.on('match:creator_left', ...)
ws.on('match:opponent_disconnected', ...)
ws.on('match:opponent_reconnected', ...)
ws.on('match:opponent_forfeited', ...)

What Is Working Well

The frontend game plugin contract is the right design and should be the model for the server side:

  • GameProps = { matchCtx?: MatchContext; onWinner?: (addr: string) => void } — two fields, typed, stable. Adding a game client-side means: create files under frontend/src/games/<slug>/, add one entry to GAMES[]. Done.
  • MatchGate and MatchSettler are correctly separated: creation/join UI vs result UI, each reading only what it needs from matchStore. No overlap.
  • server/settlement.ts is a clean three-function module with no game knowledge — settleMatch, cancelMatchOnChain, abortMatchOnChain. It should stay exactly as-is.
  • server/protocol.ts is a canonical type file for all 38 WS events with a note to keep client in sync — the right instinct, even if the sync is still manual.

The server plugin pattern just needs to catch up to what the frontend already achieved.

Recommended Sequence

Ordered by impact-to-effort ratio given the stated plan (all games → server-authoritative, next game arriving soon):

  1. Create server/src/games/registry.ts — define GamePlugin interface and registry (~20 lines, new file)
  2. Move PacManServerGame to server/src/games/pacman/PacManServerGame.ts — extract, register, delete from match.ts
  3. Remove game-slug branches from match.ts — replace three if (gameSlug === …) blocks with plugin dispatch. match.ts loses ~100 lines.
  4. Add serverAuthoritative: boolean to games.ts — one field, explicit execution model per game
  5. Group matchStore WS handlers by concern — section comments only, zero runtime change, immediate debugging benefit

Steps 1–3 together make adding the next server-authoritative game a matter of creating one new file with no edits to lifecycle code.
