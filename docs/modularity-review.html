Critical Issues

I2 — Three Parallel State Machines with No Shared Contract CRITICAL

What is shared The semantics of the match lifecycle — what states exist, what transitions are valid, and what each state means to the business.

How it is shared Implicitly. There is no single canonical type. Each layer defines its own enumeration independently:

Contract (Rust)     → Pending | Active | Complete | Refunded | Cancelled            (5 states)
Server Redis (TS)   → waiting | joined | active | settling | complete |             (9 states)
                       settlement_failed | disputed | abort_failed | cancelled
Frontend Zustand    → idle | creating | waiting | joining | ready | countdown |     (11 states)
                       playing | settling | complete | settlement_failed | disputed
StrengthFunctional (implicit)
DistanceHigh — cross-system + cross-process
VolatilityHIGH — core domain, stated pain point

The match lifecycle is the core subdomain of this application. Yet the three components that implement it share no typed boundary. The coupling is implicit: each layer assumes the others agree on the meaning of each state, but nothing enforces that agreement.

The distance makes this worse. Contract ↔ server is a system boundary (blockchain ↔ Node.js). Server ↔ frontend is a process boundary (WebSocket). At each boundary, the implicit contract is "we both know what settling means." When you add a new phase — rematch_pending, tournament_queued — you add it to all three independently, with no compiler telling you when you've missed one. You named adding match modes as your primary pain point. This is the structural cause.

Recommended direction Define a single canonical match status type that all three reference. The server ↔ frontend gap is addressable immediately with no new infrastructure:

// shared/match-protocol.ts — one source of truth
export const MATCH_STATUS = {
  WAITING:            'waiting',
  JOINED:             'joined',
  ACTIVE:             'active',
  SETTLING:           'settling',
  COMPLETE:           'complete',
  SETTLEMENT_FAILED:  'settlement_failed',
  DISPUTED:           'disputed',
} as const
export type MatchStatus = typeof MATCH_STATUS[keyof typeof MATCH_STATUS]

Server Bet.status and frontend matchStore.phase both import from this. The contract's status strings are then validated at the server's CosmWasm response boundary — one explicit assertion point, not three silent assumptions.

I1 — WebSocket Event Protocol as an Implicit 30-Event Schema HIGH

What is shared The entire operational protocol between server and frontend — 30+ event type strings, each with its own payload shape, each encoding assumptions about what data will be present.

How it is shared By convention. The server emits:

send(creator, 'match:begin', { matchId, p1: activeBet.creator, p2: activeBet.opponent })

The frontend receives:

ws.on('match:begin', (raw) => {
  const data = raw as { p1: string; p2: string }
  // ...
})
StrengthFunctional
DistanceModerate — different processes
VolatilityHIGH — grows with every new feature

There is no schema, no contract file, no generated types. The as { p1: string; p2: string } cast is a runtime assumption, not a compile-time check. Adding a field, renaming a key, or adding a new event requires manual search across two codebases. Mismatches surface at runtime.

This is also where game plugging costs compound: a new game type that needs custom WS coordination (e.g., a turn-based game needing game:turn_change) has no typed place to register that contract.

Recommended direction A single shared protocol definition, importable by both sides:

// server/src/ws/protocol.ts (or a shared workspace package)
export interface WsEvents {
  'match:begin':           { matchId: string; p1: string; p2: string }
  'match:opponent_joined': { matchId: string; opponent: string }
  'match:countdown':       { matchId: string; seconds: number }
  'game:state':            { matchId: string; [key: string]: unknown }
  // ...
}

Type the server's send() function and frontend's ws.on() against this map. You get autocomplete on event names and payload shapes, and a compiler error when they diverge. This is additive — it formalises what already implicitly exists.

Moderate Issues

I6 — Winner Consensus Logic Inside the Transport Handler MODERATE

handleGameOver / doSettle / markDisputed in ws/handlers/match.ts (lines 302–369) implement the core competitive rule: both players must report the same winner within 10 seconds, or the match is disputed. This is a meaningful business rule — the timeout duration, the NX gate, and the dispute condition are design choices that will change as the platform grows.

StrengthIntrusive — transport ↔ business logic mixed
DistanceLow — same file
VolatilityHIGH — consensus rules are core

These 70 lines live inside the WebSocket handler, directly interleaved with Redis calls, message routing (send()), and telemetry. The consensus logic cannot be invoked or tested without a live WS connection and Redis instance. Changing the resolution strategy — adding a trusted arbiter for tournament disputes, adjusting the timeout per game type — requires modifying a function that is simultaneously responsible for transport, state mutation, and business logic.

The low distance keeps this from being critical — it is co-located and will co-evolve. But it is the structural bottleneck for competitive mode evolution.

Recommended direction Extract the consensus decision to a pure function:

// ws/handlers/consensus.ts
export function evaluateGameOver(
  from: string,
  winner: string,
  otherReport: string | null,
  bet: Bet
): { action: 'settle' | 'dispute' | 'wait'; winner?: string }

The handler calls this and acts on the decision. The consensus rules become testable and changeable without touching the transport layer. This is a ~30-line extraction.

Notable — Low Volatility Saves It

I3 — Dual Contract Clients Without Shared Types LOW

frontend/lib/escrow.ts and server/chain/settlement.ts both independently encode the CosmWasm ExecuteMsg interface as plain JavaScript objects. The Rust source is the authoritative schema; neither TypeScript file references it.

StrengthModel — duplicated knowledge
DistanceHigh — cross-system
VolatilityLOW — contract is stable once deployed

Model coupling at cross-system distance is technically unbalanced, but low volatility saves it. CosmWasm contracts are effectively immutable without migration. The message shapes are small and stable. The risk is low unless a migration or new execute variant is planned.

When this becomes a problem Contract migration, adding a new execute variant, or introducing a second contract. At that point, the absence of shared types will cause missed updates in one client.

Recommended direction Nothing urgent. When the next contract change is needed, co-locate a contract-interface.ts that both clients import. Many CosmWasm projects generate these from the schema JSON — worth exploring at migration time.

Healthy Patterns

GameProps — A Minimal Contract Boundary HEALTHY

interface GameProps {
  matchCtx?: MatchContext
  onWinner?: (addr: string) => void
}

This two-field interface is the entire coupling surface between the match system and any game. Game engines are pure functions with zero external imports. PacManGame and ShooterGame do not know what a matchStore is. Adding a new game requires implementing the engine, registering it in games.ts, and nothing else.

The onWinner callback is particularly clean: the game reports a fact ("player at this address won"), and the match system decides what to do about it. Games have no knowledge of wallets, WebSockets, or settlement. This is contract coupling at low distance — exactly right for a moderately volatile integration.

In-Memory Match Map for the Hot Path HEALTHY

During an active game, state packets and input events are relayed through an in-memory Map<matchId, Match> with no Redis hop. Only the match lifecycle (create, join, settle) touches Redis. This is the right partition: volatile, high-frequency game data stays local; durable match state is persisted. The design will not require change when throughput grows — game relay is already O(1) with no I/O.

Atomic Redis NX Gates HEALTHY

The NX (set-if-not-exists) pattern in handlePlayerReady and doSettle correctly prevents double-countdown and double-settlement races when both players send ready/game-over simultaneously. This is correct distributed systems design for a single-node Redis deployment.

Summary

IssueSeverityEffort
Three parallel state machines, no shared contract (I2) CRITICAL Medium — shared constants file, derive server + frontend from one source
WS protocol as implicit 30-event schema (I1) HIGH Low — one typed protocol definition file, type send() and ws.on()
Consensus logic inside transport handler (I6) MODERATE Low — ~30-line extraction to a pure function
Dual contract clients without shared types (I3) LOW Low — defer to next contract migration
The two critical issues share a root cause: the match lifecycle domain has no explicit, enforced representation that all components agree on. The WS protocol is one expression of that domain; the state machines are another. Fixing I2 first (canonical status types) will naturally reduce the scope of I1 (fewer implicit event-to-status assumptions). Neither fix requires architectural change — both are additive type definitions that make existing implicit contracts explicit.
